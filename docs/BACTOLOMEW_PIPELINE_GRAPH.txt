BACTOLOMEW PIPELINE GRAPH
Specification for drawing a flow chart figure. Derived from the code in
/home/bals/Documents/dev/BACTolomew and from one completed reference run
runs/sample_78eaa9126850/run_78eaa9126850 (153 genomes, Acinetobacter baumannii).
Plain text, no markdown. Read sections 3 and 4 as the authoritative graph.


1. PURPOSE

BACTolomew takes a folder of assembled bacterial genomes and runs one sequential
pipeline over them: assembly QC, Bakta annotation, MLST and cgMLST typing, plasmid
reconstruction, pangenome and recombination analysis, two phylogenies, fastGEAR lineage
inference, and a DIAMOND screen of the annotated CDS against marker protein databases,
all merged into one annotation table held in memory.
The figure should convey three things: which stages run once per genome and which
consume the whole cohort, which arrows carry real data between stages and which are only
execution order, and that the databases are prepared once outside any run.


2. HOW TO READ THIS FILE

Section 3 gives the nodes first, each with a stable id on its own labelled line.
Section 4 gives the edges as "from_id -> to_id : what flows". Edges refer to nodes only
by the ids in section 3; no edge names a node that is not listed there.
An edge marked "[order only, no data]" exists because the Runner calls one step after the
other, not because data moves. Draw those faintly, or as a separate execution spine, and
never as data flow.
An edge marked "[gate, no data]" is a control or freshness condition enforced by the code:
the downstream stage refuses to run, or refuses to be reused, without the upstream one,
but no file passes between them. Draw those dashed.
Node "type" is one of input, database, process, output.


3. NODE LIST

  INPUTS

    id:        user_genomes
    label:     Genome assemblies
    type:      input
    tool:      none. CLI --genomes <folder> collected by FastaUtils.collect_fastas, or the
               GUI genome picker in startup_dialog.py.
    runs:      once, before the pipeline
    optional:  no. CLI.read_arguments errors with "--genomes is required when not using
               --GUI", and the config builder raises SystemExit 1 when the folder holds no
               FASTA.
    inputs:    user input: one assembled nucleotide FASTA per genome, .fna / .fa / .fasta
    outputs:   nothing in the run directory. The absolute paths are recorded in
               run_config.json inputs.genomes and run_state.json inputs.genomes. 153 files
               under /Data/ST492/final_fasta in the reference run.
    note:      A SAMPLE is one input assembly FASTA. The sample name is Path.stem, for
               example GCA_000804885.1, and it names every per-sample directory
               downstream. DataInput rejects two files with the same stem or the same
               name after stripping .gz and the FASTA suffix (find_genome_name_collisions,
               also used by the GUI genome picker), listing the colliding paths. The
               genomes are never copied into the run directory except as sanitized or
               staged copies, in bakta_tmp/, assembly_qc/checkm2_input/ and the MOB-suite
               per-sample dirs; the tools read the originals at their absolute host paths,
               which is why those paths are bind-mounted into the container.

  DATABASES AND SETUP

    id:        datainput
    label:     Validate inputs
    type:      process
    tool:      pure Python: pipeline.DataInput dataclass __post_init__, built by
               CLI.workflow_cfg or by the GUI startup_dialog.py. Merges
               bactolomew_config.json, loaded by ToolEnv._load_app_config, with the CLI
               flags --output, --bakta_db, --mobsuite_db, --checkm2_db, --cores,
               --dmnd_threads, --bakta_threads, --window_length.
    runs:      once per run
    optional:  no. The CLI aborts with SystemExit 1 when --bakta_db, --queries or
               --compound are missing, when fastgear.image is unset, or when
               validate_chewbbaca_settings fails. DataInput raises ValueError
               "bakta_db: required" or "bakta_db: directory not found", and on duplicate
               marker or genome stems.
    inputs:    user input: genome folder, output directory, core budget, DB path
               overrides. Database: bactolomew_config.json sections runtime, container,
               envs, envs_root, databases, bakta_db, chewbbaca, assembly_qc, fastgear,
               mobsuite. Paths from user_genomes, db_bakta, db_markers, db_compound and
               db_cgmlst must all resolve.
    outputs:   an in-memory DataInput object; nothing on disk yet. Its fields are what
               later appear as run_config.json inputs.*
    note:      Resolves every path, forces diamond = bakta = True regardless of the flags,
               so Bakta can never be switched off, creates the output directory, and picks
               the Snippy reference. The code default is
               sorted(self.genomes, key=lambda p: (p.stem, str(p)))[0], which for this
               cohort would be 20038ENE2.fna, but the reference run recorded
               snippy_reference = /Data/ST492/final_fasta/GCA_028622775.1.fna, so the
               reference was supplied explicitly: startup_dialog.py line 850 passes
               inputs["snippy_reference"] back from an existing run_config.json when a run
               is resumed. Do NOT caption the figure "reference auto-selected".

    id:        run_dir_init
    label:     Open run directory
    type:      process
    tool:      pure Python: the Runner._run_workflow_impl preamble
               (_compute_thread_plan, _build_run_config, _build_expected_outputs,
               _write_run_lock, _flush_run_state), wrapped by run_workflow in
               make_container_context / set_container_context.
    runs:      once per run
    optional:  no
    inputs:    stage datainput: the validated DataInput object. Stage tools_runtime: the
               container runtime and image used to build the bind-mount context.
    outputs:   the run directory itself, runs/<sample_set_id>/<run_id> in GUI mode or any
               --output folder in CLI mode; run_config.json with created_at,
               sample_set_id, run_id, annotation_id_strategy, inputs, thread_plan,
               output_dir; expected_outputs.json, 2199 predicted absolute paths in the
               reference run, all of which exist on disk; run.lock.json, present while the
               run is live and deleted by the finally block; run_state.json with status
               "running"; <output>/.bactolomew_home, the container HOME, absent from this
               run directory.
    note:      sample_set_id = "sample_" + sha1 of the sorted unique genome stems joined
               by "|", truncated to 12 characters, so the same cohort always reuses the
               same directory. An existing run_config.json in the folder is read back
               first (after RunValidation.genome_set_change_error has refused, with
               Runner.GenomeSetChangedError, a folder whose recorded genome set differs
               from the given one), which is how a resumed run keeps its run_id and its
               annotation_id_strategy "sorted_bakta_json_v1". run.stop is deleted here;
               creating that file later makes the next _check_stop raise RunStoppedError.
               thread_plan in the reference run: total_cores 104; bakta, assembly_qc,
               mobsuite, chewbbaca, diamond_makedb and panaroo 32; mlst, diamond_blastx,
               gubbins and phylogeny_raxml 64; phylogeny_snippy 16. run_config.json also
               records inputs.bakta_threads = 104 and inputs.dmnd_threads = 104, which are
               NOT what is passed to the tools.

    id:        tools_runtime
    label:     Tool runtime
    type:      database
    tool:      one unified container image, bactolomew-tools:0.1.0, from
               bactolomew_config.json container.image, holding every tool as a conda env;
               built or pulled by ContainerRuntime.ensure_tools_image. The configured
               runtime is "docker".
    runs:      once, outside the run
    optional:  no: every tool call goes through ToolEnv.tool_cmd / conda_tool_cmd.
    inputs:    user input and configuration: bactolomew_config.json runtime
               (docker, singularity or native), container.image, envs_root, envs;
               docker/Dockerfile or a configured registry.
    outputs:   a local docker image, or a .sif for singularity, or, with runtime "native"
               or BACTOLOMEW_NATIVE, the per-tool conda prefixes under envs/:
               assembly_qc, bakta, chewbbaca, diamond, fasttree, gubbins, mlst, mobsuite,
               panaroo, phylogeny, platon, snippy.
    note:      ToolEnv._container_prefix wraps each call as
               docker run --rm --user uid:gid -e HOME=<out>/.bactolomew_home
               [--memory Ng] -v root:root ... -w <dir> bactolomew-tools:0.1.0
               conda run --no-capture-output -n <env> <exe>.
               Host directories are bind-mounted at IDENTICAL paths so absolute path
               arguments resolve unchanged. _tool_env_key maps bakta to bakta; diamond to
               diamond; mob_recon and mob_typer to mobsuite; snippy, snippy-core and
               raxml-ng to phylogeny; run_gubbins.py to gubbins; panaroo to panaroo;
               chewbbaca to chewbbaca; mlst to mlst; quast, quast.py and checkm2 to
               assembly_qc. fastGEAR is the one exception: raw argv through
               ToolEnv.container_image_cmd against the SAME tools image, with no
               conda run. A native runtime turns each call into
               conda run -p envs/<env> <exe>. run_report.json for the reference run has
               tools.used == [] and tools.versions == {}, that is, not a single external
               tool was launched, so that run cannot tell you which runtime was used.

    id:        db_bakta
    label:     Bakta database
    type:      database
    tool:      prepared once outside a run. DbDownload.install_bakta (first-time setup) runs
               conda run -n bakta bakta_db download --output <dest> --type full
               inside the tools image (a light DB installed earlier still works).
    runs:      once, outside the run
    optional:  no in practice. DataInput raises ValueError "bakta_db: required" or
               "bakta_db: directory not found", and Runner.run_bakta raises
               FileNotFoundError if the resolved path is missing. Only if CFG.bakta_db
               were empty would run_bakta_on_fastas omit --db and let bakta fall back to
               its own configured DB, and DataInput makes that unreachable.
    inputs:    database: the downloaded Bakta reference DB directory
    outputs:   a directory outside the run dir: /Shared/bakta_db_full/db/db, recorded as
               bactolomew_config.json bakta_db and run_config.json inputs.bakta_db
    note:      pure input node, nothing in the run directory. Added to the container bind
               roots by make_container_context so bakta sees it at the identical path
               inside the image.

    id:        db_checkm2
    label:     CheckM2 database
    type:      database
    tool:      prepared once outside a run: a prebuilt CheckM2 DIAMOND reference file.
    runs:      once, outside the run
    optional:  yes, overridable with --checkm2_db. If checkm2_database_path is blank the
               --database_path flag is omitted and CheckM2 uses its own configured DB. It
               was set in the reference run.
    inputs:    database: uniref100.KO.1.dmnd, installed once
    outputs:   envs/assembly_qc/checkm2_db/CheckM2_database/uniref100.KO.1.dmnd, recorded
               as bactolomew_config.json assembly_qc.checkm2_database_path and in
               run_config.json inputs.assembly_qc
    note:      consumed only by assembly_qc. ToolEnv.make_container_context explicitly
               appends configured_assembly_qc_settings()["checkm2_database_path"] to the
               bind roots.

    id:        db_markers
    label:     Marker sequence catalogue
    type:      database
    tool:      prepared once outside a run; read by DbCatalog.load_db_catalog and
               load_db_catalog_index. In GUI mode the marker file list IS the catalog,
               through startup_dialog._load_catalog_entries over MARKER_DB_CATALOG_PATH;
               in CLI mode the user points --queries at a file or folder and the catalog
               is used only to look up each stem's category.
    runs:      once, outside the run
    optional:  no. CLI --queries is required, SystemExit 1 is raised if the catalog cannot
               be loaded, and DataInput requires at least one marker FASTA with unique
               stems.
    inputs:    database: marker protein FASTAs under DB/seq/markers/ plus
               DB/catalogs/marker_db_catalog.json, which gives each file a category and an
               optional resistance_metadata pointer
    outputs:   DB/seq/markers/*.fasta, and the stem to category map
               DataInput.marker_categories, recorded as run_config.json
               inputs.marker_categories
    note:      the repo holds 13 marker FASTAs TODAY (AMRF_core-AMR, AMRF_core-BMRG,
               AMRF_plus-AMR, AMRF_plus-BMRG, AMRF_plus-VIRULENCE,
               BacMet2-EXP-database_BMRG, CARD_AMR, CGE-MGE-Prot_MOBILE,
               CGE-PlasmidFinder-Prot_PLASMID, CGE-VirulenceFinder-Prot_VIRULENCE,
               ISFinder-Prot_MOBILE, Phaster-Prophage-Virus-Prot_PHAGE,
               VFDB-setB-Prot_VIRULENCE) and marker_db_catalog.json has the same 13
               entries. The reference run used 14: run_config.json inputs.marker_sequences
               also lists COGorg24_COG.fasta, with inputs.marker_categories
               COGorg24_COG = "COG". That file and its catalog entry have since been
               removed from the repo. Do not caption the figure "14 marker DBs in
               DB/seq/markers" as a present-tense fact.

    id:        db_compound
    label:     Compound element catalogue
    type:      database
    tool:      prepared once outside a run; read by DbCatalog.load_db_catalog_index.
    runs:      once, outside the run
    optional:  no. CLI --compound is required, the run aborts if no FASTA is found, and
               DataInput requires at least one.
    inputs:    database: reference-locus and compound-element protein FASTAs plus
               DB/catalogs/compound_db_catalog.json
    outputs:   DB/seq/compound/PAIDB-PathogenicityResIslands_RESISTANCE.fasta, the only

               {"PAIDB-PathogenicityResIslands_RESISTANCE": ""}, an EMPTY category.
    note:      these are the DIAMOND subjects for diamond_reference_loci, searched against

    id:        db_resistance_meta
    label:     Resistance metadata
    type:      database
    tool:      prepared once outside a run; resolved by DbCatalog through the
               resistance_metadata catalog entry, with
               DbCatalog.KNOWN_MARKER_RESISTANCE_METADATA as fallback, and parsed by
               ResistanceMetadata.py.
    runs:      once, outside the run
    optional:  conditional: only 5 marker stems carry resistance metadata; the other
               markers simply get none and their hits keep empty Resistance* columns.
    inputs:    database: DB/metadata/AMRF/ReferenceGeneCatalog.txt and
               DB/metadata/CARD/aro_index.tsv
    outputs:   no run-directory file. The resolved map is recorded in run_config.json
               inputs.marker_resistance_metadata, which in the reference run holds exactly

               source CARD.
    note:      consumed only inside collect_annotations, by
               ResistanceMetadata.enrich_marker_hits_with_resistance and
               build_annotation_resistance_maps. No external tool reads it.

    id:        db_cgmlst
    label:     cgMLST schemes
    type:      database
    tool:      prepared once outside a run. src/pipeline/ChewbbacaSchemaBuild.py is pure
               Python: it normalizes allele FASTAs and pickles chewBBACA's .schema_config
               and .genes_list itself, so no chewBBACA PrepExternalSchema call is needed.
               It is invoked ONLY from the GUI schema import dialog
               (src/annotation_explorer_polars/schema_import_dialog.py), never from
               Runner.py or any workflow module.
    runs:      once, outside the run
    optional:  the BUILD is optional and happens outside a run; the schema DIRECTORY is
               not optional when chewbbaca runs. validate_chewbbaca_settings is called at
               CLI time and again as the very first statement of
               Runner._run_workflow_impl, so an unusable schema aborts the entire pipeline
               before any stage starts.
    inputs:    user input: a cgMLST source, which can be an already-built chewBBACA schema
               directory, a folder or .zip of per-locus allele FASTAs, a combined
               multi-locus FASTA or a single-locus FASTA, plus a schema id or species slug
               and the MLST scheme aliases to register
    outputs:   DB/cgmlst/<schema_id>/<locus>.fasta, 2390 locus FASTAs for
               acinetobacter_baumannii; DB/cgmlst/<schema_id>/short/<locus>_short.fasta;

               .schema_config records bsr 0.6, translation_table 11, size_threshold 0.2,

               scheme_species_catalog.json, rewritten atomically and sorted by schema_id;
               bactolomew_config.json chewbbaca.available_schemas[<schema_id>], 34 schemas
               in the shipped config, written inside a bare try/except that swallows
               failures.
    note:      draw as ONE database node feeding chewbbaca's -g <schema_dir> plus the
               catalog that ChewBBACAWorkflow._select_runtime_schema reads. Nothing from
               it is written into the run directory. The reference run used
               DB/cgmlst/acinetobacter_baumannii, and run_config.json inputs.chewbbaca
               records schema_dir, genes_list and catalog_path explicitly.

    id:        db_mobsuite
    label:     MOB-suite database
    type:      database
    tool:      prepared once outside a run; the path is passed through
               ToolEnv.configured_mobsuite_settings.
    runs:      once, outside the run
    optional:  yes: when empty the --database_directory flag is simply omitted.
    inputs:    database: a MOB-suite database directory, from config
               mobsuite.database_directory / db_path / database / db, or --mobsuite_db
    outputs:   a MOB-suite DB directory. UNSET in this repo: bactolomew_config.json has
               "mobsuite": {}, run_config.json inputs.mobsuite is
               {"database_directory": "", "extra_args": []}, and mobsuite/summary.json
               records database_directory "", so mob_recon used the DB bundled in the
               mobsuite conda env.
    note:      when set it is added to the container bind roots by make_container_context.
               The bundled fallback DB's path and version cannot be determined from the
               repo or the run directory.

  PER SAMPLE STAGES

    id:        bakta
    label:     Bakta annotation
    type:      process
    tool:      bakta, through ToolEnv.tool_cmd("bakta"), that is
               conda run --no-capture-output -n bakta bakta inside
               bactolomew-tools:0.1.0; natively conda run -p envs/bakta bakta.
               Utils.bakta_allowed_versions pins "bakta 1.10.4".
    runs:      per sample
    optional:  not user-optional, DataInput forces CFG.bakta = True. Two reuse gates. Run
               level: when every bakta/<stem>/<stem>.json and .gff3 exists and
               _validate_bakta_reuse_outputs passes, the step closes as
               "reused_existing_output" and ran_bakta is set True without calling bakta,
               which is what the reference run did. Per sample: a genome whose
               bakta/<sample>/<sample>.json already exists is skipped inside the loop.
    inputs:    user input: one genome FASTA per sample. Each is first rewritten by
               FastaUtils.prepare_query_fasta with write_map=False into
               bakta_tmp/<sample>.fna, with every defline replaced by contig_<int>; bakta
               runs on that sanitized copy, never on the original. Database: db_bakta,
               passed as --db.
    outputs:   bakta/<sample>/<sample>.{json,gff3,tsv,txt,faa,ffn,embl,gbff,
               hypotheticals.faa,hypotheticals.tsv,inference.tsv,log} plus <sample>.fna,
               which is the sanitized input copied back in and not a bakta product:
               13 files x 153 samples = 1989 entries, all in expected_outputs.json.
               bakta_tmp/<sample>.fna, 153 sanitized inputs left behind after the run and
               NOT in expected_outputs.json.
    note:      per sample but a plain sequential for-loop in one process; the concurrency
               is inside bakta through --threads thread_plan["bakta"] =
               min(total_cores, 32) = 32 here. Flags: --force --output
               bakta_tmp/<sample>__bakta_out --threads --prefix <sample>
               --keep-contig-headers plus --skip-trna --skip-tmrna --skip-rrna
               --skip-ncrna --skip-ncrna-region --skip-crispr --skip-sorf --skip-gap
               --skip-ori --skip-plot --skip-pseudo, so this stage effectively yields CDS
               calls only. The tree is copytree'd from bakta_tmp into bakta/<sample>, the
               sanitized FASTA is copied in as <sample>.fna, and the temp dir is deleted.
               Per-sample failures are accumulated and raised as one RuntimeError at the
               end of the loop. Downstream: <sample>.json and <sample>.fna feed
               collect_annotations; <sample>.gff3 plus .fna appended after ##FASTA feeds
               panaroo. NOT produced here: the 93 bakta/<sample>/<sample>.fna.fai files on
               disk, which were written out of band; do not draw them.

    id:        mlst
    label:     MLST typing
    type:      process
    tool:      mlst, the tseemann tool, with its bundled PubMLST database, in the mlst
               conda env inside the tools image. MlstWorkflow._resolve_mlst_base_cmd
               probes mlst --version then --help through
               ToolEnv.conda_tool_cmd("mlst"), falling back to bare mlst on PATH. No
               --scheme is ever passed, so mlst auto-detects.
    runs:      per sample, with cohort output
    optional:  not user-optional. Skipped by reuse when _validate_mlst_reuse_outputs finds
               both files non-empty and results.json covering every input genome stem,
               which is what the reference run did. A failure raises and aborts the run.
    inputs:    user input: the assembly FASTA files, one mlst process per genome.
               Database: the PubMLST typing database shipped inside the mlst env, not a
               path the pipeline configures.
    outputs:   mlst/results.csv with columns sample, input_file, scheme, sequence_type and
               alleles joined by ";"; mlst/results.json, one object per genome with
               sample, input_file, scheme, sequence_type and alleles[]
    note:      the ONLY stage with real intra-stage parallelism:
               ThreadPoolExecutor(max_workers=max(1, min(threads, len(genomes), 64))),
               with threads = min(total_cores, min(64, n_genomes)) = 64 here. Results are
               collected, sorted by (sample, input_file) and written once as a cohort CSV
               and JSON pair, so it is per-sample compute with cohort output. Any
               per-genome failure is re-raised as one RuntimeError after all futures
               finish, so partial output is never written. All 153 samples carry scheme
               abaumannii_2 in the reference run. mlst consumes nothing from assembly_qc
               or bakta. Its one real data edge out is mlst/results.json to chewbbaca.

    id:        mobsuite
    label:     Plasmid reconstruction
    type:      process
    tool:      mob_recon from MOB-suite, through ToolEnv.tool_cmd("mob_recon"), that is
               conda run -n mobsuite mob_recon inside bactolomew-tools:0.1.0; natively
               conda run -p envs/mobsuite mob_recon. Flags: --infile --outdir
               --num_threads --sample_id <stem> --force, plus --database_directory only
               when configured, plus mobsuite.extra_args.
    runs:      per sample, with cohort output
    optional:  not user-optional, there is no flag to disable it. Skipped by reuse when
               _validate_mobsuite_reuse_outputs finds the three tracked files present,
               non-empty, parseable and covering every genome with status success, which
               is what the reference run did.
    inputs:    user input: each genome FASTA, first rewritten by
               FastaUtils.prepare_query_fasta with write_map=True into a temp dir with
               deflines renamed to contig_<N>. Database: db_mobsuite, unset in this repo,
               so mob_recon used its bundled DB.
    outputs:   mobsuite/contigs.tsv, tracked, cohort-wide, 15770 data rows;
               mobsuite/plasmids.tsv, tracked, 642 data rows; mobsuite/summary.json,
               tracked, with database_directory, threads, sample_count 153,
               plasmid_contig_count, plasmid_count and per-sample records;
               mobsuite/per_sample/<sample>/, 153 directories, NOT tracked, each with
               contig_report.txt, mge.report.txt, chromosome.fasta, <sample>.fna (the
               sanitized query), command.stdout.log and command.stderr.log, plus
               mobtyper_results.txt in 143 of them, biomarkers.blast.txt in 146, and
               plasmid_<CLUSTER>.fasta or plasmid_novel_<md5>.fasta where plasmids were
               reconstructed.
    note:      hybrid: mob_recon runs once per genome in a plain sequential for-loop, with
               parallelism inside mob_recon through --num_threads = min(cores, 32) = 32,
               but the three top-level tables are cohort-wide and written once after the
               loop. Per-genome failures are APPENDED to a failures list and re-raised as
               one RuntimeError after the loop, not raised immediately. Each sample runs
               into a TemporaryDirectory under the run dir and is copytree'd to
               mobsuite/per_sample/<sample> only on success. Post-processing reclassifies
               MOB-recon calls: a contig keeps IsPlasmid true only with direct evidence,
               that is a replicon, relaxase, MPF or oriT type or accession, or a
               mobilizable or conjugative PredictedMobility; otherwise Prediction becomes
               "plasmid_similarity_only" or "chromosome", and plasmids.tsv is filtered to
               rows with direct evidence. SCHEMA DRIFT: mobsuite/contigs.tsv on disk has
               28 columns and no PlasmidID, while MOBSUITE_CONTIG_COLUMNS in the current
               code defines 29 with PlasmidID fourth; plasmids.tsv matches its coded
               columns. mob_typer is added to tools_used but is never invoked directly:
               mob_recon calls it internally, so keep it inside this node. The 7
               mobsuite/per_sample/<s>/<s>.fna.fai files are out-of-band artefacts; do not
               draw them.

    id:        snippy_per_sample
    label:     Snippy variant calling
    type:      process
    tool:      snippy in the phylogeny conda env inside the tools image. Per genome:
               snippy --cpus <snippy_threads> --outdir <tmp>/snippy/per_sample/<stem>
               --ref <reference fasta> --ctgs <genome fasta>. Implemented in
               PhylogenyWorkflow._run_snippy_per_sample.
    runs:      per sample
    optional:  part of the single Runner step "phylogeny" and skipped with it on reuse.
               The reference genome is excluded from the loop, so a single-genome cohort
               produces no sample directories and the snippy branch is bypassed entirely:
               a trivial one-taxon Newick is written to trees/raw/snippy_core.raxml.nwk
               instead. Since the phylogeny rework of 2026-10 the step reruns only when the
               Snippy tree itself is missing or invalid (no Gubbins gate).
    inputs:    user input: every genome FASTA except the reference, iterated sorted by
               (stem, str(path)); the reference genome FASTA CFG.snippy_reference,
               /Data/ST492/final_fasta/GCA_028622775.1.fna in the reference run, supplied

               nucleotide sequence. Stage diamond_markers: dmnd/queries/*.dmnd, passed
               explicitly as query_db_files. Stage mobsuite: mobsuite/contigs.tsv and
               plasmids.tsv, re-read off disk by Runner._attach_mobsuite_predictions and
               load_mobsuite_contig_predictions. Database: db_markers, through
               DB/catalogs/marker_db_catalog.json for the per-DB category, and
               db_resistance_meta, through ReferenceGeneCatalog.txt and aro_index.tsv.
    outputs:   annotations/bakta_vs_queries/bakta_annotations_nt-vs-<marker db>.tsv, 14
               files, all in expected_outputs.json. NO annotation table on disk: the
               merged DataFrame, 574416 rows, recorded as run_state.json
               steps.collect_annotations.rows, is returned in memory to run_workflow and
               discarded. The code comment is explicit: "No CSVs are written; annotations
               are kept in-memory only."
    note:      cohort-scoped: all samples' CDS go into ONE temporary FASTA,
               bakta_annotations_nt.fasta, written by AnnotationUtils.write_annotation_
               fasta into a TemporaryDirectory under the run dir and deleted as soon as
               DIAMOND returns, so it is NOT a persisted file despite naming every output
               TSV. DIAMOND therefore runs 14 times per run, not per genome.
               parse_multiple_bakta_json keeps only features of type "cds" and parses the
               contig number back out of the sanitized contig_<n> header. AnnotationUtils
               stamps Method = "bakta", derives AnnotationCategory from the product text,
               and assigns stable ids BKT0000001 onward over the sorted-JSON row order,
               run_config.annotation_id_strategy "sorted_bakta_json_v1", frozen so a
               resumed run keeps the same ids. After the search: read_annotations computes
               Subject_coverage = Align_len / S_len * 100 and derives Method and
               MarkerCategory by splitting the file stem after "-vs-";
               collapse_diamond_annotations keeps one best hit per AnnotationID and DB,
               grouping by DB and not by Method, so AMRF core and plus and
               AMR / BMRG / VIRULENCE are not merged; ResistanceMetadata joins AMRF rows
               by protein or nucleotide accession and CARD rows by ARO then protein
               accession, yielding ResistanceMetadataSource, Alleles, GeneFamilies,
               DrugClasses, Antibiotics and Mechanisms; infer_annotation_category_and_
               source reduces the hits to ConsensusCategory, ConsensusSource and
               ConsensusDonorProduct by CATEGORY_PRIORITY_MAP; then assign_gene_ids and
               _attach_mobsuite_predictions add 15 MobSuite* columns joined on Sample and
               normalized Contig. The mobsuite edge is an enrichment dependency rather
               than a blocking one: with no mobsuite output the MobSuite* columns are
               simply NA. Runtime: about 14 of the 15 minutes of the otherwise fully
               reused reference run. AnnotationUtils.add_compound_clusters and compute_gene
               have no caller anywhere under src/, so no stage exercises them.

  OUTPUTS

    id:        run_finalize
    label:     Validate and report
    type:      output
    tool:      pure Python: RunValidation.validate_completed_run plus
               Runner._build_run_report, _flush_run_state and _clear_run_lock, in the
               finally block, so it also runs on failure or stop.
    runs:      once per run
    optional:  no: it is in a finally block, so it produces a report for a failed or
               stopped run too.
    inputs:    all twelve step results and the whole run directory
    outputs:   run_report.json with start and end time, status, inputs, per-step records,
               tools, output_dir and the full output_files listing, 12488 entries in the
               reference run; run_state.json with final status "success" and
               outputs_validated true; run.lock.json is deleted, although it is still
               listed in run_report.json output_files, which is how you can tell the
               report is written just before the lock is cleared. The report is also
               printed to stdout.
    note:      RESULT_REQUIRED_STEPS is exactly the twelve Runner steps. Any step whose
               status is "success" but whose outputs fail validate_step_outputs is
               downgraded to "partial", and the run status becomes failed, partial or
               success accordingly. tools.used is EMPTY in this report, because every step
               was reused and no external tool was ever launched. If the figure needs a
               single terminal artifact, the honest one is the run directory plus
               run_report.json, NOT an annotation table: collect_annotations writes no
               merged table to disk.

7. NOTES AND CAVEATS

  Execution order. Verified against the twelve literal _step_start calls in
  Runner._run_workflow_impl, Runner.py lines 1278 to 1726, strictly sequential in one
  Python thread: assembly_qc, bakta, mlst, mobsuite, panaroo, core_alignment,
  gubbins, core_tree, phylogeny, fastgear_clades, chewbbaca, diamond_markers, diamond_reference_loci,
  collect_annotations, then the finally block, which runs validate_completed_run and
  writes run_report.json and run_state.json and clears run.lock.json. There is no
  scheduler, no DAG object and no branch that reorders them. run_state.json for the
  reference run lists the steps in exactly this order.

  Nothing runs in parallel at stage level. Runner.py has no ThreadPoolExecutor,
  ProcessPool, multiprocessing or asyncio. The only concurrency in the whole pipeline
  package is inside MlstWorkflow.run_mlst. bakta, mobsuite, snippy and
  diamond_reference_loci are plain for-loops; their per-stage concurrency is the tool's
  own --threads or --cpus, taken from _compute_thread_plan. The figure may show data
  edges cutting across the chain, but it must NOT show two stages side by side as
  concurrent without saying so in the caption.

  Every stage is skippable by reuse, not by configuration. The pattern is identical: run
  the stage's validator against the existing run directory and, if clean, close the step
  with reason "reused_existing_output" without launching the tool. collect_annotations is
  the sole stage with no reuse path, although it does reuse the 14 marker-hit TSVs when
  they validate. Eleven of the twelve steps in the reference run are marked
  reused_existing_output; only collect_annotations actually did work. So "optional" in
  section 3 almost always means "reusable", not "configurable off".

  The only hard gates the code enforces beyond data flow:
    1. panaroo on bakta, through the ran_bakta flag. If not ran_bakta, panaroo is
       "skipped" with reason "bakta_not_run". Because it is skipped and not failed, a
       Bakta-less run does not stop at panaroo, it stops at gubbins.
    2. core_alignment on panaroo: raises "Panaroo output required before the core
       alignment can be ordered."
    3. Freshness by input stamps (since 2026-10): core_alignment, gubbins, core_tree
       and fastgear_clades are reused only when the sha256 of their input, their
       parameters and the tool version match what they recorded; a changed input reruns
       the step and everything downstream of it, with the reason logged.

  The three phylogeny sub-nodes are ONE Runner step. snippy_per_sample, snippy_core and
  raxml_snippy_tree are all inside the single step named "phylogeny".
  They succeed or fail together and are reused together. If the figure prefers a single
  box, collapse them and label the box "per-sample Snippy plus cohort RAxML".

  Do not draw QC as a filter. Nothing downstream reads assembly_qc/summary.tsv and no
  stage is gated on the Quality column. No code filters CFG.genomes on it.

  Dead code, one footnote at most.
  AnnotationUtils.add_compound_clusters and compute_gene have no caller under src/.
  The max_target_seqs=1 argument of run_diamond_annotations is dead.

  Files on disk that belong to no stage. All 12587 files in the reference run are
  attributable except 100 .fai index files: 93 under bakta/<sample>/ and 7 under
  mobsuite/per_sample/<sample>/. run_report.json output_files is exactly 100 entries
  short of the current disk set and the missing 100 are precisely those; their mtimes,
  2026-08-21, postdate the run and every other file; and a grep for samtools, faidx or
  pysam across src/ finds nothing. They were written out of band. Do not draw them.
  Three leftover temporary directories are also not outputs:
  annotations/reference_loci/tmpedwy_4n4 and tmpvq5wkvn2, from interrupted DIAMOND calls,
  and gubbins/tmp1tj7krj1, from an interrupted Gubbins run.

  Unresolved: which runtime and which tool versions the reference run used.
  run_report.json records tools.used == [] and tools.versions == {}, because every step
  was closed as reused_existing_output and tools_used.add is only reached in the non-reuse
  branches. Runtime "docker" and image bactolomew-tools:0.1.0 come from the current
  bactolomew_config.json, not from the run. The mlst version, the PubMLST DB version and
  the installed chewBBACA version could not be established read-only; the string 3.5.4
  comes only from the SCHEMA_CONFIG dict that ChewbbacaSchemaBuild writes into
  .schema_config. Do not put tool version numbers in the figure except bakta 1.10.4,
  which Utils.bakta_allowed_versions pins.

  Unresolved: the run's own timestamps are internally inconsistent. run_state.json and
  run_report.json record 2026-07-03T13:46 to 14:01, but the files have mtime 2026-07-08
  14:02, and the contents of mlst/, chewbbaca/out and bakta/*.log span 28 May, 3 June and
  8 July. The directory is a faithful record of WHICH files each stage produces, but not
  of when, nor with what commands.

  Unresolved: the run id. runs/sample_78eaa9126850/run_78eaa9126850 matches no generator
  in the code; _new_attempt_id produces
  sample_<sha1 first 12>__run_<YYYYmmdd_HHMMSS_ffffff>. It was either passed in as
  DataInput.run_id or the directory was renamed by hand. Do not present "run_<hash>" as
  the naming convention.

  Unresolved: there is no terminal annotation artifact. collect_annotations writes no
  annotation table anywhere; the 574416-row DataFrame is returned to run_workflow and
  discarded. Whatever consumes it, the annotation_explorer_polars GUI and its cache,
  reads the run directory separately, outside the pipeline package. If the figure needs a
  terminal artifact, use the run directory plus run_report.json.

  Phylogeny rework of 2026-10 (PHYLOGENY_REWORK_2026-10-10.md). The reference run's
  files described above (gubbins/input, trees/core_gene_tree.nwk, trees/snippy_raxml.tree,
  fastgear/input) predate it; a resume rebuilds core_alignment, gubbins, core_tree and
  fastgear_clades and moves the Snippy tree to trees/raw/.

  fastGEAR image discrepancy. bactolomew_config.json sets
  fastgear.image = "pgcbioinfo/fastgear:latest" and the CLI and GUI refuse to start
  without it, but no code path runs that image: the launch uses the run's own
  bactolomew-tools:0.1.0. Label the node with the latter.

  Marker database count. The run used 14 marker FASTAs including COGorg24_COG.fasta with
  category "COG"; the repo holds 13 today and marker_db_catalog.json has 13 entries. Say
  "14 in this run" or "13 in the repo today", not a bare present-tense count.

  Snippy reference. GCA_028622775.1.fna was supplied explicitly, not chosen by the code's
  default, which would have picked 20038ENE2.fna. Do not caption it as auto-selected.

  MOB-suite table schema drift. mobsuite/contigs.tsv on disk has 28 columns and no
  PlasmidID, while MOBSUITE_CONTIG_COLUMNS in the current code defines 29 with PlasmidID
  fourth. Do not caption contigs.tsv as carrying a PlasmidID.

  Minor and unverified. _find_fasta_for_gff falls back to a warning and writes a Panaroo
  input GFF without its ##FASTA block if the matching Bakta .fna is missing, which
  Panaroo would likely reject; all 153 prepared GFFs exist in this run, but not every one
  was opened to confirm its ##FASTA block. ChewbbacaSchemaBuild.register_schema writes
  into bactolomew_config.json inside a bare try/except, so a schema could be in the
  catalog without appearing in chewbbaca.available_schemas; not all 34 were checked.
